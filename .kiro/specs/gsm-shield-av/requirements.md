# Requirements Document

## Introduction

GSM Shield AV is a Windows-only antivirus application purpose-built for the GSM phone repair and flashing market. Technicians in this market regularly use low-level USB flashing tools (Odin, SP Flash Tool, Miracle Box, UFI Box, and many others) that general-purpose antivirus engines — including Windows Defender — flag and delete as threats, because those tools interact with USB drivers and device memory in ways that resemble malware.

GSM Shield AV solves this by shipping with deep knowledge of the GSM tool ecosystem. It maintains a pre-built and user-extensible whitelist of known-safe GSM tools, performs SHA-256 hash-based trust checks before any scan, and replaces Windows Defender as the registered antivirus on the machine via the Windows Security Center API. Real-time file-system monitoring is implemented in user space via Chokidar. Scanning is powered by bundled ClamAV binaries. Licensing is enforced through Keygen.sh. The product is distributed as a single EXE installer produced by Inno Setup 6.

## Glossary

- **Application**: The GSM Shield AV Electron desktop process (renderer + main process combined).
- **Scanner**: The module responsible for invoking ClamAV `clamscan.exe` and parsing its output.
- **Monitor**: The Chokidar-based real-time file-system watcher.
- **Whitelist**: The combined set of pre-built GSM tool hashes and user-added entries stored in SQLite.
- **Cloud_Whitelist**: The authoritative list of verified GSM tool hashes served by the cloud backend.
- **Quarantine_Store**: The locked folder inside the user's AppData directory where infected files are moved.
- **Database**: The SQLite database stored in the user's AppData directory containing the five canonical tables: `whitelist`, `quarantine`, `scan_history`, `settings`, `telemetry`.
- **Service**: The node-windows background Windows service that keeps real-time protection active across reboots.
- **License**: A Keygen.sh license key bound to one or more machine fingerprints.
- **Machine_Fingerprint**: A SHA-256 hash derived from CPU ID, disk serial number, and MAC address, generated by `node-machine-id`.
- **WSC**: Windows Security Center — the Windows subsystem that tracks the registered antivirus product.
- **Defender**: Windows Defender Antivirus (also referred to as Microsoft Defender).
- **Tray**: The Windows system-tray icon managed by the Application.
- **Installer**: The single EXE installer produced by Inno Setup 6.
- **Backend**: The Node.js + Express server hosted on Railway.app backed by PostgreSQL.
- **FreshClam**: The ClamAV definition-update utility (`freshclam.exe`) bundled with the Application.
- **Threat**: Any file identified by the Scanner as containing malware (ClamAV FOUND result).
- **Grace_Period**: A 7-day window during which the Application accepts a previously validated license without network connectivity.
- **Feature_Gate**: A restriction applied to Application functionality when no valid License is present.
- **Submission**: A community-submitted hash + name + vendor record sent to the Backend for review.

## Requirements

---

### Requirement 1: Local Database Initialization

**User Story:** As a technician, I want the application to set up its own local database automatically on first run, so that I never need to configure anything before using the product.

#### Acceptance Criteria

1. WHEN the Application starts for the first time on a machine, THE Database SHALL be created in the platform-standard AppData directory for the current Windows user.
2. THE Database SHALL contain exactly five tables on creation: `whitelist`, `quarantine`, `scan_history`, `settings`, and `telemetry`.
3. WHEN the Application starts and the Database already exists, THE Database SHALL apply any pending schema migrations before any other operation reads from or writes to the Database.
4. IF a schema migration fails, THEN THE Application SHALL log the error to a file in AppData and display a non-fatal error message to the user without crashing.
5. THE `settings` table SHALL be populated with default values on first creation so that the Application has a valid configuration state before the user changes any settings.

---

### Requirement 2: GSM Whitelist — Pre-Built Entries

**User Story:** As a technician, I want the application to ship with a pre-built list of known-safe GSM tools, so that those tools are never flagged or deleted by the scanner.

#### Acceptance Criteria

1. THE Whitelist SHALL include SHA-256 hash entries for executables belonging to at least the following tools on initial installation: Odin3, SP Flash Tool, Miracle Box, UFI Box, NCK Box, Z3X Pro, Infinity CM2, Chimera Tool, MRT Dongle, EFT Pro Dongle, Hydra Tool, Pandora Box, Volcano Box, GPG Dragon, Sigma Box, Furious Gold, ATF Box, Easy JTAG, Riff Box, and Falcon Box.
2. WHEN the Scanner receives a file path, THE Scanner SHALL compute the SHA-256 hash of the file and query the Whitelist before invoking `clamscan.exe`.
3. IF a file's SHA-256 hash matches any entry in the Whitelist, THEN THE Scanner SHALL mark the file as trusted and SHALL NOT invoke `clamscan.exe` for that file.
4. THE Whitelist table SHALL store at minimum: `hash` (TEXT, primary key), `name` (TEXT), `vendor` (TEXT), `verified` (INTEGER flag), and `source` (TEXT: "bundled", "user", or "cloud").
5. WHEN a Whitelist entry is displayed in the UI, THE Application SHALL show the `verified` flag to distinguish pre-built and cloud-synced entries from user-added entries.

---

### Requirement 3: GSM Whitelist — User-Managed Entries

**User Story:** As a technician, I want to add my own tools to the whitelist, so that custom or regional flashing software I use is never scanned.

#### Acceptance Criteria

1. WHEN the user selects a file through the Add File dialog on the Whitelist page, THE Application SHALL compute the SHA-256 hash of the selected file and insert a new entry into the Whitelist with `source` = "user" and `verified` = 0.
2. IF the SHA-256 hash of a file being added already exists in the Whitelist, THEN THE Application SHALL notify the user that the file is already trusted and SHALL NOT create a duplicate entry.
3. WHEN the user removes a user-added Whitelist entry, THE Application SHALL delete that entry from the Whitelist and SHALL NOT delete pre-built or cloud-sourced entries through the same action.
4. THE Whitelist page SHALL provide a search bar that filters visible entries by `name` or `vendor` in real time as the user types.
5. WHERE the License is inactive, THE Application SHALL cap user-added Whitelist entries at 10 and SHALL display a prompt to activate a License when the cap is reached.

---

### Requirement 4: GSM Whitelist — Cloud Sync

**User Story:** As a technician, I want the whitelist to stay up to date with newly verified tools, so that I never have to manually add tools that have already been verified by the community.

#### Acceptance Criteria

1. WHEN the Application starts and the License is active, THE Application SHALL attempt to sync the Whitelist from the Backend endpoint `GET /whitelist` once per 24-hour period.
2. WHEN a sync response is received from the Backend, THE Application SHALL upsert all returned entries into the Whitelist with `source` = "cloud" without deleting user-added entries.
3. IF the Backend is unreachable during a sync attempt, THEN THE Application SHALL silently retry using exponential back-off and SHALL NOT display an error to the user unless the sync has failed for more than 72 consecutive hours.
4. WHEN the user clicks "Sync from Cloud" on the Whitelist page, THE Application SHALL immediately trigger a sync regardless of the 24-hour schedule and SHALL display a progress indicator during the operation.
5. THE Application SHALL record the timestamp of the last successful sync in the `settings` table and display it on the Whitelist page.

---

### Requirement 5: Community Tool Submission

**User Story:** As a technician, I want to submit tools I trust to the community whitelist, so that other users benefit from my local knowledge of safe GSM software.

#### Acceptance Criteria

1. WHEN the user clicks "Submit a Tool" on the Whitelist page and completes the submission form with a file hash, tool name, and vendor name, THE Application SHALL send a POST request to the Backend endpoint `POST /submissions`.
2. WHEN the Backend accepts a submission, THE Application SHALL display a confirmation message stating the submission is pending review.
3. IF the Backend returns an error or is unreachable during submission, THEN THE Application SHALL display a descriptive error message and SHALL retain the submission data in the form so the user can retry.
4. THE Application SHALL validate that the hash field contains a valid 64-character hexadecimal SHA-256 string before submitting.

---

### Requirement 6: ClamAV Scan Engine

**User Story:** As a technician, I want the application to scan files for real malware using a proven engine, so that I am protected without needing to install separate antivirus software.

#### Acceptance Criteria

1. THE Application SHALL bundle `clamscan.exe`, `freshclam.exe`, and all required ClamAV DLLs within the installed application directory so that ClamAV does not need to be installed separately on the machine.
2. THE Application SHALL bundle `main.cvd` and `daily.cvd` virus definition files so that scanning is available immediately after installation without a network connection.
3. WHEN the Scanner invokes `clamscan.exe`, THE Scanner SHALL pass `--no-summary`, `--infected`, and the target path as arguments and SHALL parse standard output for lines containing the keyword `FOUND` to identify threats.
4. WHEN the Scanner completes a scan of a file or directory, THE Application SHALL write a record to the `scan_history` table containing: target path, scan start time, scan end time, number of files scanned, number of threats found, and the scan mode (single file, directory, quick, full).
5. IF `clamscan.exe` exits with a non-zero code that does not indicate a found threat (exit code 2 or higher), THEN THE Application SHALL log the error and display a descriptive message to the user without crashing.
6. IF the `main.cvd` or `daily.cvd` files are missing or corrupted at startup, THEN THE Application SHALL display a non-dismissable warning banner prompting the user to run a definition update and SHALL disable scanning until valid definitions are confirmed.

---

### Requirement 7: Scan Modes

**User Story:** As a technician, I want multiple scan modes, so that I can choose between speed and thoroughness depending on the situation.

#### Acceptance Criteria

1. WHEN the user initiates a Quick Scan, THE Scanner SHALL scan the following directories: Desktop, Downloads, Temp (`%TEMP%`), and AppData Roaming — excluding the Quarantine_Store path.
2. WHEN the user initiates a Full Scan, THE Scanner SHALL scan all fixed and removable drives visible to the operating system — excluding the Quarantine_Store path.
3. WHEN the user initiates a Folder Scan, THE Application SHALL present a folder-picker dialog, and THE Scanner SHALL scan the selected directory recursively — excluding the Quarantine_Store path.
4. WHEN the user initiates a File Scan, THE Application SHALL present a file-picker dialog, and THE Scanner SHALL scan the selected file.
5. WHILE a scan is in progress, THE Application SHALL display a progress bar and the path of the file currently being scanned, updated at most every 500 milliseconds.
6. WHILE a scan is in progress, THE Application SHALL display a Cancel button that, when clicked, terminates the `clamscan.exe` process and marks the scan record in `scan_history` as cancelled.
7. THE Scanner SHALL apply the Whitelist check described in Requirement 2 Acceptance Criterion 2 to every file before passing it to `clamscan.exe`, regardless of scan mode.

### Requirement 8: Virus Definition Updates

**User Story:** As a technician, I want the virus definitions to stay current, so that the scanner can detect newly discovered malware.

#### Acceptance Criteria

1. WHEN the user clicks "Check for Updates" in the Settings page update section, THE Application SHALL invoke `freshclam.exe` with appropriate flags to download updated definition files to the bundled definitions directory.
2. WHILE `freshclam.exe` is running, THE Application SHALL display a progress indicator and the current download status as reported by `freshclam.exe` standard output.
3. WHEN `freshclam.exe` completes successfully, THE Application SHALL display the new definition version and the date of the update.
4. IF `freshclam.exe` fails or the network is unreachable, THEN THE Application SHALL display a descriptive error message without crashing and SHALL retain the existing definition files.
5. THE Application SHALL display the current definition version and date of last successful update on the Settings page at all times.

---

### Requirement 9: Quarantine

**User Story:** As a technician, I want detected threats to be moved to a safe quarantine area instead of immediately deleted, so that I can review and restore files if they are false positives.

#### Acceptance Criteria

1. WHEN the Scanner identifies a Threat and auto-quarantine is enabled in settings, THE Application SHALL move the original file to the Quarantine_Store directory and record the original path, threat name, detection timestamp, and file hash in the `quarantine` table.
2. THE Quarantine_Store directory SHALL be excluded from all Chokidar monitoring paths to prevent re-scanning quarantined files.
3. WHEN the user selects a quarantine entry and clicks "Restore", THE Application SHALL move the file back to its original path and remove the entry from the `quarantine` table.
4. WHEN the user selects a quarantine entry and clicks "Delete Permanently", THE Application SHALL securely delete the file from the Quarantine_Store and remove the entry from the `quarantine` table.
5. THE Quarantine page SHALL display a warning banner stating that restoring files may expose the system to malware.
6. IF the original path of a quarantined file no longer exists at restore time (directory deleted), THEN THE Application SHALL prompt the user to choose an alternative restore destination.

---

### Requirement 10: Real-Time File System Protection

**User Story:** As a technician, I want the application to automatically scan new and modified files as they appear, so that threats are caught immediately without requiring manual scans.

#### Acceptance Criteria

1. WHEN real-time protection is enabled, THE Monitor SHALL watch the following paths for file creation and modification events: Desktop, Downloads, `%TEMP%`, `%PROGRAMFILES%`, `%PROGRAMFILES(X86)%`, and AppData Roaming.
2. THE Monitor SHALL only trigger scans for files with the following extensions: `.exe`, `.dll`, `.msi`, `.bat`, `.cmd`, `.vbs`, `.ps1`, `.js`, `.scr`, `.com`, `.zip`, `.rar`, `.7z`.
3. WHEN a file event is detected by the Monitor for an eligible extension, THE Monitor SHALL wait 2 seconds after the last write event to that path before passing the file to the Scanner (awaitWriteFinish delay).
4. WHEN the Monitor passes a file to the Scanner and the Scanner identifies a Threat, THE Application SHALL automatically move the file to the Quarantine_Store and display a Windows system notification containing the threat name and file name.
5. THE Monitor SHALL apply the Whitelist check before invoking `clamscan.exe` for every file event, consistent with Requirement 2 Acceptance Criterion 2.
6. THE Quarantine_Store path SHALL be explicitly excluded from the Monitor's watch paths at all times, including when the user adds custom monitored paths.
7. WHEN the user adds or removes a custom monitored path in Settings, THE Monitor SHALL update its active watch list within 5 seconds without requiring an application restart.
8. WHILE real-time protection is disabled, THE Monitor SHALL not watch any paths and THE Tray icon SHALL display the gray (protection off) state.

### Requirement 11: Background Service

**User Story:** As a technician, I want real-time protection to remain active after I reboot my machine, so that I am always protected without having to manually start the application.

#### Acceptance Criteria

1. WHEN the user enables "Start with Windows" in Settings, THE Application SHALL register a Windows background service via node-windows that starts the Monitor at system boot before any user logs in.
2. WHEN the user disables "Start with Windows" in Settings, THE Application SHALL remove the background service registration.
3. WHEN the Service detects a Threat, THE Service SHALL write a threat event record to a JSON log file in AppData so that the Application window can read and display it via IPC when it next opens.
4. IF the Service fails to start, THEN THE Application SHALL display an error notification to the user and set the Tray icon to the gray (protection off) state.
5. THE Service SHALL be stopped and unregistered by the Installer's uninstall sequence.

---

### Requirement 12: System Tray and Window Behavior

**User Story:** As a technician, I want the application to live in the system tray and stay out of my way, so that protection runs silently in the background.

#### Acceptance Criteria

1. WHEN the user clicks the close (X) button on the Application window, THE Application SHALL hide the window and remain running in the Tray rather than exiting.
2. THE Tray icon SHALL display one of three states: green (real-time protection active, no threats), red or yellow (threat detected or quarantine action needed), or gray (real-time protection off).
3. WHEN the Tray icon is right-clicked, THE Application SHALL display a context menu with exactly three items: "Open", "Quick Scan", and "Exit".
4. WHEN "Exit" is selected from the Tray context menu, THE Application SHALL terminate the Electron process.
5. WHEN "Quick Scan" is selected from the Tray context menu, THE Application SHALL open the main window to the Scanner page and immediately start a Quick Scan.
6. WHEN a Threat is detected by the Monitor or Scanner, THE Application SHALL update the Tray icon to the red or yellow threat state and display a Windows system notification.

### Requirement 13: Application UI — General Shell

**User Story:** As a technician, I want a clean, professional interface that is easy to navigate, so that I can manage protection settings without confusion.

3. THE Application SHALL provide a persistent sidebar with navigation links to exactly six pages: Dashboard, Scanner, Whitelist, Quarantine, Settings, and License.
4. THE Application SHALL use React Router for client-side navigation between the six pages without reloading the Electron window.

**User Story:** As a technician, I want a dashboard that shows me the current protection status at a glance, so that I know immediately whether my system is safe.

**User Story:** As a technician, I want a settings page where I can configure protection behavior, monitored paths, and update schedules, so that I can adapt the application to my workflow.

### Requirement 19: License Page

**User Story:** As a technician, I want to activate and manage my license from within the application, so that I can unlock full functionality without leaving the app.

#### Acceptance Criteria

1. THE License page SHALL display the current license status (active or inactive), the license expiry date when active, and the Machine_Fingerprint.
2. THE License page SHALL provide an input field for the license key and an "Activate" button.
3. WHEN the user enters a license key and clicks "Activate", THE Application SHALL send the key and Machine_Fingerprint to the Keygen.sh activation API and display success or failure feedback within the page.
4. WHEN activation succeeds, THE Application SHALL store the encrypted license token (AES-256) in AppData and update all Feature_Gates immediately without requiring a restart.
5. THE License page SHALL provide a "Deactivate" link that removes the current machine from the License via the Keygen.sh API and clears the stored license token.
6. THE License page SHALL display a link to the purchase page for users who do not yet have a license key.

### Requirement 20: License Validation and Feature Gating

**User Story:** As a product owner, I want licensing to be enforced at runtime, so that only paying customers can use the full feature set.

#### Acceptance Criteria

1. WHEN the Application starts, THE Application SHALL silently validate the stored license token against the Keygen.sh validation API.
2. IF the Keygen.sh API is unreachable at startup and a valid license token was stored within the last 7 days, THEN THE Application SHALL treat the license as valid for the current session (Grace_Period).
3. IF the stored license token is absent, expired, or invalid and the Grace_Period has elapsed, THEN THE Application SHALL apply the following Feature_Gates: limit scanning to one folder with a maximum of 50 results, cap user-added Whitelist entries at 10, and disable real-time protection.
4. THE Application SHALL never embed the Keygen.sh admin token in the Electron application bundle; only validation-scoped tokens SHALL be used in the Application.
5. WHEN the License transitions from inactive to active, THE Application SHALL remove all Feature_Gates immediately without requiring a restart.

### Requirement 21: Windows Defender Replacement

**User Story:** As a technician, I want the application to replace Windows Defender as the active antivirus, so that Defender no longer interferes with GSM flashing tools.

#### Acceptance Criteria

1. WHEN the Application runs its first-run setup sequence with administrator privileges, THE Application SHALL execute PowerShell scripts with `ExecutionPolicy Bypass` and `-NonInteractive` flags to disable Defender real-time monitoring, behavior monitoring, and on-access scanning via `Set-MpPreference`.
2. WHEN the first-run setup sequence runs, THE Application SHALL apply Group Policy registry keys (`DisableAntiSpyware` = 1 under the appropriate HKLM path) and disable Tamper Protection via the registry.
3. WHEN the first-run setup sequence runs, THE Application SHALL stop and disable the `WinDefend` Windows service.
4. WHEN the first-run setup sequence runs, THE Application SHALL register itself with WSC by writing the required registry entries (including `ProductState` = 266240) so that WSC reports GSM Shield AV as the active antivirus.
5. WHEN the Installer's uninstall sequence runs, THE Application SHALL reverse all registry changes, re-enable the `WinDefend` service, and restore Defender to its default operational state.
6. IF any PowerShell step in the first-run setup sequence fails, THEN THE Application SHALL log the failure with the exact error output and continue the remaining steps rather than aborting the entire sequence.

### Requirement 22: Installer

**User Story:** As a technician, I want a single-file installer that guides me through setup, so that I can install the application without technical knowledge.

#### Acceptance Criteria

1. THE Installer SHALL be a single `.exe` file produced by Inno Setup 6 and SHALL require administrator privileges to run.
2. THE Installer SHALL present a multi-step wizard with the following steps in order: welcome screen with application name and version, license agreement, installation folder selection, optional desktop shortcut creation, installation progress, and completion screen.
3. THE Installer SHALL copy all application files, ClamAV binaries and DLLs, bundled virus definitions, PowerShell scripts, and application assets to the selected installation directory.
4. THE Installer SHALL NOT execute Defender-disable or WSC-registration steps; those SHALL be performed by the Application itself on first run.
5. THE Installer's uninstall sequence SHALL stop and remove the background Service, re-enable Defender, remove all application registry entries including the WSC registration and startup entry, delete all installed files, and optionally prompt the user to delete AppData user data.

### Requirement 23: Build and Packaging Pipeline

**User Story:** As a developer, I want a reproducible three-stage build pipeline, so that I can produce a release-ready installer from source consistently.

#### Acceptance Criteria

1. THE build pipeline Stage 1 SHALL invoke Vite to compile the React renderer into a production bundle.
2. THE build pipeline Stage 2 SHALL invoke `electron-builder` targeting Windows x64 to produce an unpacked application directory and an ASAR archive.
3. THE build pipeline Stage 3 SHALL invoke Inno Setup 6 to compile the unpacked application directory into the final single-file installer EXE.
4. WHEN a new installer version is available, THE Application SHALL display an in-app notification with a download link and SHALL NOT perform automatic silent updates.
5. WHEN `freshclam.exe` completes a definition update, THE Application SHALL confirm that the updated definition files are valid before replacing the bundled definitions, so that a failed partial download does not disable scanning.

### Requirement 24: Cloud Backend

**User Story:** As a product owner, I want a minimal cloud backend to serve the verified whitelist and accept community submissions, so that all users benefit from a centrally maintained list of safe GSM tools.

#### Acceptance Criteria

1. THE Backend SHALL expose a `GET /whitelist` endpoint that returns all entries from the `cloud_whitelist` table where `status` = "verified" as a JSON array.
2. THE Backend SHALL expose a `POST /submissions` endpoint that accepts a JSON body containing `hash`, `name`, and `vendor` fields and inserts a record into the `submissions` table with `status` = "pending".
3. THE Backend SHALL authenticate all API requests using a static API key passed in the `Authorization` header; requests without a valid key SHALL receive a 401 response.
4. IF the `hash` field in a `POST /submissions` request is not a valid 64-character hexadecimal string, THEN THE Backend SHALL return a 422 response with a descriptive error message.
5. THE Backend SHALL be deployable as a single `server.js` entry point with route files for `/whitelist` and `/submissions`.

---

### Requirement 25: Offline and Error Resilience

**User Story:** As a technician, I want the application to behave gracefully when there is no internet connection, so that I can work in environments without reliable network access.

#### Acceptance Criteria

1. IF the network is unavailable during a Whitelist sync attempt, THEN THE Application SHALL continue operating normally using the locally cached Whitelist data.
2. IF the network is unavailable during a license validation attempt and the Grace_Period has not elapsed, THEN THE Application SHALL allow full functionality for the current session.
3. IF the network is unavailable when the user initiates a definition update, THEN THE Application SHALL display a friendly message stating that the update requires an internet connection and SHALL retain existing definitions.
4. IF the network is unavailable when the user submits a tool, THEN THE Application SHALL display a descriptive error and SHALL preserve the submission form data for retry.
5. THE Application SHALL never crash due to a network timeout or connectivity failure; all network calls SHALL be wrapped in error handlers with defined fallback behavior.
